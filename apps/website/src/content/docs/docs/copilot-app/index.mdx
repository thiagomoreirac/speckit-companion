The board sits next to the chat in the GitHub Copilot app. It lists every spec in the project, opens the one you select, and runs the next step from a button. [Install](/docs/install) puts it there.

## What the board shows

| Part | What you see |
| --- | --- |
| Spec list | Each spec's status, a four-step bar (specify, plan, tasks, implement) and its task count, most recently active first. Filter by Active, Done or All; narrow Done to completed or archived; search by name, number or source with fuzzy matching; or sort by number, name, creation date, modification date or pipeline step. The sort choice is saved per repository in the session. Bulk lifecycle actions apply to the eligible specs in the current group. Open a spec to copy its path or folder name. |
| Pipeline | The four steps of the open spec, each marked Not started, Running or Done |
| Next-step card | The step that comes next and the button that runs it, with the command it sends on the line below |
| Document tabs | The spec, plan, tasks, research, data model and checklists, rendered as they are in the VS Code viewer |
| Overview tab | The same record as [the Overview in VS Code](/docs/results/the-overview) |
| Activity tab | The run history, newest first |

When the agent creates a spec, writes `plan.md` or ticks a task, the board updates without a refresh. That includes the first spec of a project that had none.

You can also drive the board from the chat. Ask "which specs are still open?" or "show me the export spec" and the board follows.

## Choose the repository

By default the board follows its own session. It starts in the session's working directory and moves when the runtime reports that directory changed, for example when the session enters a new worktree. Each chat and each sub-session runs its own board, so parallel sessions in different worktrees never affect each other.

A Project chat usually sits in a conversation directory with no specs. The app gives a canvas no coordination context, so the board asks the runtime's session management for the sessions whose parent is this chat (`management.list`, filtered to `parentSessionId` equal to this session) and never scans other sessions. When this chat's own directory has no specs and exactly one such session exists, the board shows that session's worktree and follows it as it changes, appears or is archived. With several, the board lists them and waits: pick one in the list (or ask the agent for `select_child`), and the choice is saved like a manual one. Session management is the user's opt-in setting, which the board never turns on, and even when it is on the runtime may not report the app's Project sessions as children of the chat. The reliable route is a coordinator binding: the coordinating agent reads the child with its own `get_session` tool and calls the board's `bind_coordinated_session` action with the session id, the worktree path and a name. The board cannot verify that binding, and it does not follow later changes by itself, so the agent calls it again when the child is created, resumed, switched or moves to a new worktree. The binding is saved and outranks following. Refresh, opening a spec, running a step, **Use repository** on the directory already shown and reopening the panel all keep it. Only choosing a different directory or session replaces it, and **Disconnect from** followed by the session name (shown instead of **Follow session** while bound) clears it and returns to the chat's own directory. A bound session receives board commands through the runtime's session-management message API; if that API is unavailable or the session does not accept the message, the board reports an error and does not send it to the parent chat. The board does not observe the selected session's turn or report its progress.

**Coordinated session** refreshes when the coordinator confirms work started from the board. For sessions managed outside that flow, ask the coordinator to refresh the list with `update_coordinated_sessions`. It supplies a complete snapshot of its own nonarchived sessions, including idle sessions, using scoped app session tools. Only worktrees this board can read are selectable. For a session on another host, use **Open session** to open it in Copilot. The list and selection survive reopening, and no new session is picked automatically. An updated path for the selected session in a full snapshot rebinds the board, unless a step is in flight. If the selected session disappears or becomes inaccessible, the board marks it unavailable and retains its last repository until you choose another or disconnect.

The move waits until no step sent from the board is running or being recorded, so a run is never read from another repository. A reopened panel catches up with the current directory.

An explicit choice overrides all of that. Press **Browse…** beside **Repository directory** to choose a folder, or enter an absolute checkout path and press **Use repository**. The native picker starts at the main worktree when the current directory belongs to a Git repository, otherwise at the current board directory. It runs on the extension host: it needs a local graphical desktop (and `zenity` on Linux), so on a remote or headless host enter the path manually. The board saves the choice in the session's artifact storage, restores it after reloads and in new panels, and stops following. Press **Follow session** (or ask the agent for `use_session_directory`) to drop the saved choice. A saved directory that no longer exists is ignored and the board follows the session instead. A chosen directory must be a repository root, with a `.git` or `.specify` folder in it; anything else is refused with a message. A missing spec directory shows a warning with the scanned path.

### Start work in a dedicated session

For a change you expect to review on its own, open a spec, bug, or Ready idea and choose **Start dedicated work**. Commit and publish the spec or Companion triage record first. Check the repository, branch, revision, autonomy mode, and record shown in the confirmation. Uncommitted edits are not part of the request. **Plan**, **Tasks**, and **Implement** keep using their usual session.

Choose **Gated** (default) to pause at required human gates, or **Unattended** when your repository permits policy-driven autonomous execution. Companion reads the autonomy policy from `.specify/autonomy.json` at the cached `origin/HEAD` commit on the default branch, never from an untrusted feature branch or working tree. That policy governs `defaultMode`, `allowUnattended`, `allowAutoPr`, `allowAutoMerge`, `requiredGates`, `allowedWriteScopes`, `maxConcurrentSessions`, and `protectedPaths`. Without a verifiable `origin/HEAD`, Companion fails closed to `gated` mode with `maxConcurrentSessions: 1` and `allowAutoMerge: false`.

The board sends the confirmed request to its owning Copilot chat. That coordinator checks the live GitHub branch tip and verifies an isolated app worktree before starting work. It reuses a verified session for the same item rather than launching duplicate work. While this happens the request is pending, not confirmed. Once verified, the coordinator's completion action updates **Coordinated session** and records the durable delivery link in `.speckit-companion/delivery/` without switching your checkout or waiting for a pull request. The board does not auto-follow a dedicated session, even if it is the only child. The board itself does not create sessions or verify remote checkouts, so a host without app coordination cannot complete the handoff. If creation is uncertain, check the coordinator chat before attempting another start. Starting work does not authorize merging or bypassing required gates.

When a work item has a durable delivery record, its spec card and detail panel display its current delivery state (`Queued`, `Assigned`, `In progress`, `Awaiting gate`, `PR open`, `Merged`, `Blocked`, or `Session expired`), autonomy mode, and clickable links to its GitHub issue, pull request, check status, session, and gate. Use **Reconcile from GitHub** to ask Copilot to sync live PR and check status into the ledger. If a cloud or local session expires, choose **Recover expired session…** to hand off recovery on the existing branch and pull request without duplicating work.

Ask the agent to select a repository to use the board's `select_root` action. For an initial selection, the agent can open the canvas with `{ "root": "/absolute/path/to/repository" }`; a saved selection takes precedence so an older open input cannot undo a later choice after a reload.

Changing repositories clears the selected spec and is blocked while a step sent from the board is running. An ordinary repository selection keeps commands in the chat that owns the board and names the selected repository so relative paths resolve there. Selecting or binding a session routes commands to that exact session through the runtime's peer-message API.

## What each button sends

A run button sends a command into the chat, and your agent runs the step from there. You can also edit the open spec's Markdown directly with **Edit**; saving is refused if the file changed on disk.

| Button | Where | What it sends |
| --- | --- | --- |
| **New** | The header | Start a Spec, Bug, Idea, Pre-Spec Cards discovery or Product Change in chat, or save a Business plan or Epic locally |
| **Run plan**, **Run tasks**, **Run implement** | The next-step card | The next step for the open spec |
| **Mark complete** | The card, once every step is done | [Mark complete](/docs/steps#mark-complete) |
| **Archive**, **Reactivate**, **Set status** | The row under the card | Change the spec's lifecycle, or force a status to recover a stranded run. Each action confirms before writing the shared `.spec-context.json` record. |
| **Converge** | The row under the card for an implemented or completed spec | Check the code against the spec and add tasks for missing work |
| **Clarify**, **Checklist**, **Analyze** | The row under the card on the Spec, Plan and Tasks tabs, respectively | Run the corresponding stock Spec Kit command |
| **Create issues** | The Tasks tab | Preview the source tasks and delivery owner, then confirm before asking the chat to create issues |
| **Resume** | The card while a step is running, or the row under it | Picks a stopped run back up |
| **Doctor** | The row under the card | A health check of the run |
| **Ask Copilot** | The row under the card | A read-only question about where the spec stands |

With the Companion Spec Kit extension in the project, the buttons send `/speckit.companion.*`. Without it they send the stock Spec Kit commands, and Mark complete, Resume, Doctor, and the Companion and Auto choices on New spec aren't offered. A spec keeps the workflow it was started with, so one that was started on Spec Kit gets the stock commands even where Companion is installed.

The board spells each command the way your project registers it: `/speckit-plan` when the commands are skills, `/speckit.plan` when they're prompt files.

For a spec with a run record, use a document's **Add comment** button to save a review note on a line. Edit or remove notes in place, then use **Refine notes** to send the pending notes to the chat as targeted edits; the board marks them applied after the send succeeds. If there is no chat, copy the prompt instead and the notes stay pending. Notes that cannot be reattached to a changed document remain at the bottom of its tab.

### Carry accepted decisions into a step

When you run **Plan**, **Tasks**, or **Implement** for a selected spec, Companion can quote matching architecture decision records (ADRs) in that session's command. Each quote names the ADR and links to the exact Git revision it came from. These are references, not instructions: they cannot change the run's scope, permissions, gates, or workflow.

Keep the decisions you want Companion to cite in `.specify/decisions.json` and review them on the repository's default branch. For example:

```json
{
  "schema": 1,
  "decisions": [
    {
      "id": "ADR-001",
      "status": "accepted",
      "specs": ["specs/101-roster"],
      "summary": "Use the existing roster store rather than introducing a second store."
    }
  ]
}
```

Give each decision a unique, stable `ADR-` ID followed by up to 40 uppercase letters, digits or hyphens, starting with a letter or digit. List up to 12 exact repository-relative spec folder paths with `/` separators, using ASCII letters, digits, underscores, hyphens or dots (no globs). Use a single-line summary of at most 400 characters. Only `accepted` records are sent. Keep `proposed` or `rejected` records out of the handoff by setting that status; when replacing an older decision, set its status to `superseded` and set `supersededBy` to the new ADR ID. Duplicate IDs and malformed records are ignored. The file is limited to 32 KiB and 64 records, and each command quotes only the first four exact matches in file order.

Companion reads from the selected checkout's cached `origin/HEAD` target, not its checked-out branch or uncommitted files. It requires a direct `github.com` origin and a remote-tracking ref mapped from the default branch. The cache may lag behind GitHub; Companion does not fetch, check for freshness, or update Git references. With no catalog or no matching decisions, the command is unchanged. If Companion cannot verify the baseline or read the catalog, it logs why it skipped decision context and still sends the ordinary command.

## Workflow Builder

Open **More tools (…) → Workflow Builder** to see the same pipeline graph used in VS Code. In a project with Companion installed, edit nodes, rearrange phases, attach hooks, choose a workflow, and preview or build the resulting commands. The builder runs the installed extension's scripts and needs Python on the extension host. Saving a node creates a project copy; returning to the shipped node keeps that copy under `.speckit-companion/workflow-backups` and offers Undo. File edits are refused if the file changed since it was opened.

Without Companion, the builder shows the installed Spec Kit workflow, presets, templates and extension hooks instead. Changes to a stock hook update the project's extension registry. The Constitution button sends the command to the board's chat in the selected repository.

Open **Integrations** in Workflow Builder to inspect registered extensions, presets, workflows, bundles and persisted Spec Kit engine runs. **Inspect resolved artifacts** asks the repository-local Spec Kit CLI which command and template layers apply and which hook bindings are enabled. This is separate from what candidates declare and from the Companion graph in **Pipeline**. Registration is not proof that the active chat discovered commands or that a workflow ran successfully. Reviewed third-party packages show an install button on their candidate row in an eligible checkout. Roadmap 0.1.0 fails Spec Kit 1.4.3's script-name validation, and Intake 0.1.3 ships a separate Figma command, so neither is offered. For supported automated setup, see [Install](/docs/install#copilot-app).

**Inspect catalog sources** shows the effective search order for extension, preset, workflow and bundle catalogs, and which sources Spec Kit marks as discovery-only. The inspection does not download catalog entries or change what Companion can install. For a web catalog, the board shows only its host, not credentials or private URL details.

### Configure an installed extension

In **Integrations → Installed packages**, choose **Configure** for an extension that ships a supported field schema. Fill in the project values you want to change, select **Review changes**, then **Save settings**. The preview lists the destination and the values you entered; existing values are not shown. The owning session saves to the extension's native project file under `.specify/extensions/<id>/` and refuses to save if the file or setup metadata changed after the review. Saving does not enable the extension, run a hook, or connect to a service.

**View setup** shows declared files and available template names when the extension has no supported editor or the checkout is read-only. **Manual setup** points to extension documentation when the manifest declares a supported repository link. Companion doesn't infer values from templates or create files from them. **Enabled in Spec Kit** describes registration, and **Hooks** shows the configured project bindings it can read. Neither verifies what will run on the execution host. Local overrides, environment variables, credentials, and service authorization stay outside the editor.

### Add configuration support to an extension

Declare each native project file in `extension.yml` under Spec Kit's [`provides.config`](https://github.github.com/spec-kit/extensions/developing.html#configuration-files). For example, declare `report-config.yml` using `name` and optionally `template`, `description`, and `required`. To generate a form, ship `report-config.yml.companion-schema.json` next to the installed manifest:

```json
{
  "x-companion-version": 1,
  "type": "object",
  "required": ["format"],
  "properties": {
    "format": { "type": "string", "title": "Report format", "enum": ["brief", "detailed"] },
    "includeSummary": { "type": "boolean", "title": "Include summary" },
    "limit": { "type": "integer", "title": "Item limit", "minimum": 1, "maximum": 100 },
    "apiToken": { "type": "string", "title": "Service credential", "writeOnly": true }
  }
}
```

This sidecar is a Companion convention, not a Spec Kit validation feature. Version 1 supports a top-level object with up to 40 fields in a `.json`, `.yml`, or `.yaml` file in the extension directory. Editable properties support nonempty strings (`enum`, `minLength`, `maxLength`), booleans, numbers, and integers (`minimum`, `maximum`), with optional `title` and `description`. Only list project fields that are safe to put in shared configuration. Mark credentials or host-only inputs with `writeOnly: true` or `x-companion-host-only: true`; Companion neither reads nor accepts a value for those fields in the form. Unsupported schema rules, nested form fields, links, and local or secret filenames aren't editable. To remove a field, apply defaults, or use unsupported file syntax such as YAML aliases, edit the native configuration outside Companion.

### Reviewed extensions

**OKR Bets** registers optional hooks for framing before Specify, alignment after Specify, and measurement after Plan. Once the reviewed extension is enabled, its candidate row offers a separate **Install OKR Bet preset** action. That preset appends an overlay to the stock Specify command and the spec template; it does not replace Companion's Specify command. Use **Inspect resolved artifacts** to see the actual layers when presets are combined. Setup does not run hooks, create bets, or connect to an OKR service. Spec-local measurement plans and reviews appear under **Evidence** when the extension writes them.

**Charter** adds an optional before-Constitution hook. Installing it does not choose a registry or change the constitution. In a Bash-capable Copilot session, choose a trusted registry and review the selected fragments before composing; composition can replace the current constitution. Open the resulting constitution from **Project files → Spec Kit**.

**PDaC** uses the accepted ProductShape model as spec context. Its optional Specify, Plan and Tasks hooks can repair citations in feature documents; they do not edit the accepted model. **PDaC Product** has no lifecycle hooks and keeps Product Changes separate from delivery specs. Install and configure ProductShape separately in the owning project. Review the dry run in chat before approving and applying a change to the accepted model.

**DocGuard** adds required hooks before Specify and Tasks and after Implement. They can block work if the lifecycle registry is missing or stale, a generated spec lacks stable identity, or documentation checks fail. The Tasks preflight skill can assign a Spec ID and refresh the registry. Installing the extension does not initialize the project registry, set up CI, or install the DocGuard CLI; review DocGuard adoption in the owning chat before using the hooks.

**Wireframe** adds optional hooks to propose SVGs after Specify, review them before Plan, and compare implementation screenshots after Implement. Preview spec-local SVGs in **Evidence**. Confirm generation and design sign-off in the owning chat: sign-off can update the spec, whereas a decision in **Evidence** only records your review.

Open a spec's **Evidence** tab to browse **Documents**, **Diagrams**, **Design**, and **Verification**. Each artifact shows its current review status; an empty category tells you what is missing. **Generate evidence** previews the inputs and destination before you commit. Companion can generate a local entity diagram from a supported Mermaid ER block in `data-model.md` without using chat. With the matching extensions installed, send Spec Kit Preview a wireflow request using `spec.md`, `uc.md`, and your chosen fidelity, or send Data Model Diagram a request using `data-model.md` and Spec Kit's Bash scripts. A queued chat request is not a finished artifact. Use **Refresh artifacts** after Copilot reports the result.

**Illustrate** runs in Copilot chat, not through the board's **Generate evidence** action. Ask it to save the HTML and an exported SVG or PNG under the current spec. **Evidence** previews the image and shows the HTML as source only. Installing Illustrate from Integrations does not choose a theme, install browser export dependencies, or add lifecycle hooks.

## Product work and evidence

Use **More tools (…) → Product work** to capture a business plan or epic without creating a spec. Open a plan and choose **Draft epic from this plan** to preselect its parent. You can also record epic dependencies. Open the epic and choose **Draft linked spec** to carry its context into the spec form. The **Linked work** tab on an existing spec links back to its sources and lets you add a saved plan or epic. Reopening the board during linked spec creation looks for the exact provenance marker in one new spec; it does not resend the request.

**New → Pre-Spec Cards** sends an idea to the selected Copilot chat to explore alternative approaches. It requires the reviewed extension version from **Workflow Builder → Integrations**. Review the proposed goal, motivation, and folder name in chat; sending the request is not confirmation and the board does not write discovery files. This flow is separate from **Idea**, which starts an assessment.

**New → Product Change** sends the intended outcome and a new, unique change name to the selected Copilot chat. It needs the reviewed PDaC Product extension and an initialized ProductShape workspace with its CLI available. Continue an existing draft or establish the first accepted baseline in chat instead. Starting a draft does not create a delivery spec or authorize changes to the accepted model.

**Evidence** shows supported files inside the current spec, including Markdown, raster and SVG previews, and a limited entity-relationship preview for Mermaid ER diagrams. For recognized Spec Kit Preview wireflows, **Static prototype preview** shows the design layout and flow using Companion's styles and inert labels. **View HTML source** shows the full file. Other prototypes and diagram formats display as source. The board never runs repository HTML or loads assets referenced by a wireflow. **Explain impact in chat** sends a read-only question tied to the artifact hash and available Git revision. It asks Copilot to cite code paths and lines, to separate facts from uncertainty, and not to implement changes.

**Approve artifact** and **Request changes** record a local decision on the exact bytes you reviewed. The **Review** tab shows recorded steps for runs that explicitly declare this spec as their target and highlights the paused step. The engine’s choices are displayed as labels, not buttons. **Explain this pause in chat** asks about the blocker without selecting an artifact or advancing the run. **Review gate evidence** opens the evidence alongside the pause and ties a local decision to both the file and gate revisions. The tab flags evidence that changed and gates that moved. A local decision does not approve or resume an engine gate. **Open terminal to review run** gives you an interactive terminal in the owning session without sending a command. Runs without a per-run spec path appear in **Integrations** only.

Select **Keep a copy for comparison** before recording a decision to retain the reviewed bytes under `.speckit-companion/artifact-reviews/` in this checkout. When the file changes, **Compare with current** shows both revisions. Images render side by side when space permits; text and prototypes remain source only. Leave the option off for files you do not want to retain after editing or removing them.

### Needs your decision

Open **Decisions** on the board to see cloud gate records under `.speckit-companion/cloud-gates/` for the selected checkout, along with correlated delivery-ledger links (branch, PR, checks, and autonomy mode) and offline cross-branch gates discovered across cached local and remote-tracking branches. Paused gates appear first. Each row links to the GitHub issue and the evidence at its recorded commit, plus the receipt comment when one was recorded. **Refresh decisions** rereads local Git refs and this checkout; use **Reconcile from GitHub in chat** to ask Copilot to verify live GitHub issue comments and check runs from any device, including GitHub Web and GitHub Mobile.

Make the decision on GitHub using the instructions for that gate. Companion never submits a decision or advances a gate directly from the board. The trusted run owner can consume a verified comment manually or, in the Trailhead pilot, opt in to watching one enrolled run from the persistent Linux checkout that holds its Spec Kit checkpoint. Posting a comment does not wake a Copilot session unless a configured cloud automation or watcher handles it.

When a cloud gate is accepted and not yet recorded in `.specify/decisions.json`, **Decisions** previews it as an ADR promotion candidate. Choose **Propose ADR promotion PR in chat** to send a draft promotion request to Copilot; Companion never edits `.specify/decisions.json` directly or merges the pull request on its own.

For an **Uncertain** record, reconcile with the trusted run owner and do not retry. Companion marks evidence stale when it can read the local file and its bytes differ, and says when it could not check. Matching bytes are not confirmation that the gate is still paused or that GitHub has accepted a decision.

On Tasks, **Create issues** previews the GitHub repository, tasks file and delivery command. Generic delivery requires one `origin` URL that points directly to `github.com`. Spec Kit 1.4.3 uses the bundled GitHub extension for this action; install it in **Workflow Builder → Integrations** if the command is missing. The board also offers reviewed setup for GitHub Project Lifecycle Sync and GHP, but won't install another delivery owner while one is enabled. Installing either blocks generic **Create issues**; configure its GitHub target separately and use that extension's lifecycle. The board rechecks the destination, file and command before sending the request to Copilot; the preview itself does not write to GitHub.

## Project files, bugs and ideas

Open **More tools (…)** for **Project files** and **Settings**, or choose **Back to specs** there to return to the board.

**Project files** lists existing project instructions, steering documents, agents, skills, workspace settings and Spec Kit files. Open a file to edit it; save or discard a draft before opening another. If the file changed on disk, reopen it before saving. **Refine with Copilot** asks the chat to improve the saved file, and **Ask Copilot to create** sends a request for a new instruction, agent or skill.

**Settings** edits the selected repository's `.vscode/settings.json`. It shows whether each value comes from the repository, a default, or the host. **Use default** removes a repository override when you save. Comments and unrelated settings stay in the file. The board watches the file and updates when it changes; if you have unsaved edits, reload before saving to avoid overwriting someone else's changes.

The canvas applies spec-directory patterns, the Ideas directory, the default workflow, built-in command spelling, context instructions, and the switches for Activity, project guidance, installation hints, and step notices. Custom workflows can supply Specify, Plan, Tasks, and Implement commands plus additional phase actions. When Specify creates a spec, the board records the selected workflow in `.spec-context.json` with the shared locked writer; it blocks further steps if that write fails. A spec whose saved workflow is no longer configured is shown as unavailable instead of silently using stock commands. Configured commit and PR checkpoints are offered after their trigger and require explicit confirmation before a request is sent. The canvas does not execute a commit or create a pull request from a checkpoint, and a user confirms completion of a commit before an after-commit action becomes available. Provider-specific flags remain VS Code features. Custom commands go to the selected chat or session, or offer copy-only when `autoExecute` is off. For keys and values, see the [Companion settings reference](/docs/reference/configuration).

Invalid repository settings are shown on the board and disable command dispatch until repaired; use Settings for invalid values or Project files to fix malformed JSON. The canvas does not read VS Code user settings. Its command-spelling override is repository-scoped; VS Code still reads its machine setting for spelling. The VS Code project folder, Settings sidebar entry, and telemetry switches affect VS Code only. Choose the assistant in the Copilot composer and set [tool permissions](https://docs.github.com/en/copilot/how-tos/github-copilot-app/agent-sessions) in the app. **Open Terminal** requests a separate, interactive Copilot Terminal canvas; it does not send commands or use VS Code shell integration. If the host cannot open it from the board, or the board follows a different repository, open Terminal directly in the owning session.

Use **New → Bug or Idea → Save to canvas** to capture work without installing an extension or sending anything to chat. Open **Bugs** or **Ideas** to read each report and use **Companion triage** to set **New**, **In review**, **Ready**, or **Parked**. These labels do not change a Spec Kit verdict or gate. If the matching Spec Kit extension is enabled, you can separately ask Copilot to assess an intake, answer clarifications, or request the next workflow action. A bug review request alone does not approve or reject the engine gate.

A **Ready** idea or an idea with an extension **Go** decision can draft a linked spec or **Update existing work**. Pick a plan, epic, or spec and review the proposed change. For plans and epics the update appears alongside the product record with a link to the source idea. For specs it is appended to the reviewed Markdown document; if the document has changed, reopen the preview before applying.

## Routines

Open **More tools (…) → Routines** to create, edit, archive, and restore manual, daily, weekly, or GitHub event-driven drafts. Choose a Spec Kit command, a custom agent, an existing GitHub Actions workflow, or a GitHub Copilot Automation (with ownership and least-privilege `write_scope` validated against `.specify/autonomy.json`). The Copilot app uses local time; GitHub drafts use UTC. **Save draft** never schedules or starts anything.

The **Cloud Autonomy Pack** provides four loop-safe, human-triggered GitHub Copilot Automation blueprints (`Spec issue dispatch`, `PR CI healer`, `Gate decision bridge`, and `Delivery ledger reconciler`), each with `allow_copilot_triggers: false` and a GitHub Actions fallback template. Save any blueprint locally as an unscheduled draft or choose **Review in chat** / **Review full pack in chat** to inspect live repository automation settings before creating paused resources.

**Review setup in chat** shares the saved version with the owning Copilot session. **Find live routines in chat** asks that session for a read-only list of the current project's schedules. Use the Copilot app's **Automations** editor for local schedules, GitHub Actions for workflow schedules and runs, and GitHub Copilot Automations for repository automations. Companion does not enable schedules on its own.

After a send, a note at the foot of the board names the command. **Show prompt** opens the whole message and **Copy** copies it, which is what you need when a session has no chat to send to.

You press one button per step and the board moves on when the agent finishes. This clip follows one spec, a profile photo upload, from New spec to done.

<Steps>

1. Press **New**, select **Spec** and the **Companion** workflow, describe what you want, and press **Create spec**. When the agent finishes, the spec is in the list as **Specified** and the card offers **Run plan**.

2. Press **Run plan**. Plan turns to Done, and the plan, the research and the data model get a tab each.

3. Press **Run tasks**. The Tasks tab lists every task by phase and counts `0/6`.

4. Press **Run implement**. Implement reads **Running** until the chat turn ends, and each task is ticked as the agent finishes it, with the files it touched. If the run stops, press **Resume**.

</Steps>

## Step times without Companion

Companion records every step, so the Overview has a time for each one. In a stock Spec Kit project the board reads progress from the files instead: a written spec, `plan.md` or `tasks.md` marks its step done, and ticked tasks show how far Implement is. There the Overview times only the steps you sent from the board, because a step you typed into the chat yourself has no start the board could note.

## Known limits

- **The board is clipped after you narrow the panel.** Dragging the divider between the chat and the board leaves the board at its old width, cut off on the left, because the Copilot app doesn't resize the panel's page. Close the board and open it again after resizing.
- **VS Code host controls remain separate.** The board edits repository settings, but does not resolve VS Code's user settings, launch VS Code terminal providers, or change Copilot permissions.
- **Each session runs in a fresh worktree.** The app cuts it from your committed default branch, so it has no `node_modules`, and an implement step that runs tests installs the project's dependencies first. For the same reason, Companion's commands only resolve when they're committed as real files.
- **Opening the board starts nothing.** If your agent goes looking for work after opening it, ask "Only open it, then wait for me."
