The canvas sits next to the chat in the GitHub Copilot app. In an initialized Spec Kit repository it opens on the **Workflow**. Switch to **Specs & runs** for the spec list, documents, and run history. [Install](/docs/install) puts it there.

## Explore and manage the workflow

The map connects lifecycle stages to integrations, workflows, and hook points. A proposed participant describes its intended role, not an installed extension. Select a node or connection to inspect its sources, inputs, outputs, permissions, and validation findings. Zoom or drag the background to move around, use **Focus dependency path** to narrow the map, or switch to **Text view** for the same participants, connections, and inspector without the graph. Spec Kit configuration and Companion workflow policy changes refresh the graph without replacing an open preview. Confirmation still rechecks the reviewed inputs. Use **Validate workflow** to re-read the repository on demand.

To run a step, select it, choose a feature or supply intent as requested, and open the preview. It shows the generated invocation, expected artifacts, and hooks that may run. **Approve & dispatch** sends the invocation through the existing agent transport. It approves the dispatch, not the agent’s findings or an external change. A graph marked **Valid** only passed the structural and policy checks.

**Spec Kit Management** groups the repository’s extensions, presets, workflows and steps, bundles, catalogs, hooks, commands and skills, constitution and Charter files, templates and schemas, and features. Supported extension, preset, workflow, and step package operations use the installed Spec Kit CLI, which must be on the canvas host’s PATH. The canvas checks the needed CLI verb and flags before offering a confirmation. Install from a reviewed local package directory, or use **Register pinned GitHub workflow** for a standalone public YAML file at a full commit and supply its expected SHA-256. The canvas shows the full definition before confirmation and registers a separate verified copy without running it. The source and a receipt stay under `.speckit-companion/workflow-sources/`, even if registration fails. Catalog trust does not authorize this installation. Spec Kit can import local step and function packages before validating a workflow, so the canvas does not install or replace workflows when those packages are present. If the installed runtime or canvas has no compatible adapter, the inspector leaves the item read-only.

For a native run, **Current definition** in **Workflow & runs** offers **Copy start command** for an enabled, unblocked workflow and lists its declared inputs. A paused native run offers **Copy resume command**. Run either command from the repository root in an interactive terminal; Companion does not supply input values or execute the command.

For an enabled workflow made up of literal review gates with distinct optional `verdict_input` values, choose **Start isolated review**, then **Decide current gate** when it pauses. Isolated review also supports `if` branches with a literal boolean or a comparison such as `{{ inputs.intake == 'approve' }}` against a verdict already collected on that path. The preview shows the expected next gate or end state before you confirm. Spec Kit runs the reviewed definition in a temporary project without loading repository plugins or running agent commands. The latest isolated checkpoint stays with the Copilot session and can resume after a canvas reload. An isolated run does not write project files or resume CLI runs from the repository. For workflows without branches, configure a gate's message, rejection behavior, or `show_file` evidence from the inspector when no review is in progress. Configuration writes a project-owned Spec Kit overlay instead of changing the installed definition. Choose an inventoried feature Markdown file up to 24 KiB. The canvas shows the exact evidence and its source before confirmation and requires a new preview if the file changes.

For an isolated or guided workflow that branches on a declared string `enum`, the start form asks you to choose the input before previewing the first checkpoint. For example, `{{ inputs.track == 'extended' }}` can route to a separate review gate when `extended` is a declared choice for `track`. Companion accepts up to four such inputs; each must be required or have a declared default. The chosen values are recorded with the run and cannot be changed when resuming. These choices do not authorize any GitHub change. Free-form and secret inputs are not supported by these adapters.

The workflow graph shows project overlay declarations and flags any declared GitHub write. Choose **Inspect composed steps** to see how Spec Kit orders and attributes the steps from the installed definition and its project overlays, without running them. Isolated review accepts only the project override for literal gate settings; guided runs do not accept overlays. You can preview and confirm disabling or removing a project overlay, or re-enabling a compatible literal review overlay when no other layer is enabled, without changing the base workflow or saved checkpoints.

For an enabled workflow with up to six literal gates, each with a distinct `verdict_input`, choose **Start guided run** when at least one gate is immediately followed by a literal GitHub issue `add-label` step in the same sequence. Guided runs support the same bounded `if` conditions as isolated review. In a branched definition, a gate with `on_reject: skip` bypasses its paired write and can route to a different checkpoint. **Decide guided gate** previews the next checkpoint and records the verdict without making a GitHub change. **Review guided issue label** previews the exact issue, existing label, and GitHub CLI account for a separate confirmation. Confirming a label advances to the next gate, not to the next write. Rejecting a gate does not undo earlier confirmed writes. Changed evidence invalidates that gate’s approval, and an uncertain GitHub result stops the run without retrying. These checkpoints belong to the Copilot session and do not start or resume Spec Kit CLI runs. Other mixed workflows remain inspectable; use individual canvas actions for supported changes.

Under **Templates and schemas**, edit or remove a project Markdown template override after reviewing the current and proposed text. The canvas stores the override separately and leaves the core template, schemas, and existing specs untouched.

In **Catalogs**, register a discovery-only source, allow installations from an explicitly reviewed HTTPS source, restrict it back to discovery, or remove the project registration. The preview shows the exact config change for extension, preset, workflow, step, and bundle catalogs. These operations do not fetch the catalog, install a package, or change user and built-in sources. Allowing installations changes how Spec Kit can use the source in later operations; it does not approve any package.

For a project workflow catalog registered at a public raw GitHub JSON URL, use **Browse pinned workflows** to list standalone releases with a SHA-256. Releases can be raw YAML at a full commit or a public GitHub ZIP containing only a root `workflow.yml`; ZIP review requires Python 3 on the canvas host. Discovery-only sources can list releases but cannot register them. From an install-allowed source, choose an exact release, review the definition, and confirm registration or replacement. The canvas rechecks the catalog and digest and saves the release's provenance without running the workflow. Companion files, bundled components, and external dependencies are not installed; use a supported local package when applicable.

In **Bundles**, register or refresh a flat `bundle.yml` whose pinned components are already installed independently. Choose a local file, enter a public raw GitHub `bundle.yml` pinned to a full commit and SHA-256, or use **Browse pinned bundles** in a project bundle catalog registered at a public raw GitHub JSON URL. Discovery-only catalogs can list releases but cannot register them. A catalog can also point to a public GitHub release ZIP or a raw ZIP at a full commit. ZIPs require SHA-256, Python 3 on the canvas host, and a single root `bundle.yml`; the canvas reads that entry without extracting the archive into the repository. Spec Kit prepares the record offline in a temporary project. The canvas previews the exact record and, for GitHub sources, the reviewed manifest. Confirmation rechecks the digest and, for a catalog release, the catalog listing and trust policy. It retains provenance under `.speckit-companion/workflow-sources/`, even if saving the record fails. No packages are installed or replaced. **Remove bundle record** is available when every package can stay installed. If another flat bundle has a matching requirement, the preview shows the ownership transfer and the exact records that will change. Nested bundles, component package archives, and cascading package changes are not available in the canvas.

With released Spec Kit 1.4.1 on the host, **Install core workflow bundle** accepts a local `bundle.yml` that pins one or more shipped workflows and nothing else: `assess` at `1.0.0`, `bugfix` at `1.0.1`, and `speckit` at `1.0.2`. Omit each component's `source`. Companion stages the bundle offline and shows each exact workflow definition plus the workflow registry and bundle record. All the workflows are installed disabled; nothing runs, no existing component is replaced, and enabling a workflow is a separate action.

With Spec Kit 1.4.1, **Remove bundle and workflow** can remove a bundle-owned standalone `workflow.yml`. For a bundle containing only two or three exclusively owned workflows, use **Remove bundle and workflows**. Each workflow to be removed must match its recorded version, be disabled, and have no companion files, project overlays, or open canvas review. The canvas also requires no saved native runs or subworkflow callers outside the workflow being removed. Spec Kit verifies the removal on a temporary copy. Confirmation deletes only the reviewed definitions and updates the two reviewed registries; empty workflow directories are left in place. Other cascading package changes remain unavailable.

Select a bundle’s component connection to see its requested version and any mismatch. A version substitution recorded by Spec Kit is advisory; an unrecorded, verifiable mismatch blocks the dependency.

Standalone template presets can be replaced from a reviewed local directory. The canvas checks the replacement in a temporary project and preserves the preset's priority and enabled state. This adapter excludes command and script overrides, extension dependencies, and projects with active constitution synchronization.

Registered lifecycle hooks can be added from declarations, disabled, reordered, or removed with a preview that shows new advisories and blockers. **Test hook wiring** validates an enabled copy in memory without executing it. The Git feature-branch validation hook also offers **Run local fixture**, which checks a known branch and spec directory in a disposable local repository instead of running the repository’s agent instructions. Inspect extension-native events and the selected integration's native override separately: the override describes what Spec Kit should generate, not what a running agent has loaded. In an existing override, you can add a declared read-only handler, remove or reorder handlers, remove all handlers attributable to one extension, or change the matcher and timeout of a known read-only handler. With Spec Kit 1.4.1 (including the repository's `1.4.1.dev0` configuration) and the Copilot or Claude integration, **Suppress all native events** previews a new or replacement empty override for that integration. It suppresses built-in handlers too, but takes effect only after Spec Kit refreshes the generated settings; it does not change lifecycle or embedded hooks. Embedded hooks with unverified effects block dispatch of the matching Companion step from the graph. For hooks written as block lists, you can preview removal or reordering within an anchor in the active recipe; this requires Python 3 on the canvas host and does not rewrite generated commands.

For an empty native override, the inspector checks generated settings on disk for both the default integration and any other recorded Copilot or Claude installation. Workflow command dispatch is blocked if Spec Kit-marked entries remain or the settings can't be checked. Overrides for other installed integrations are read-only in the canvas. **Restore inherited native events** previews removing just the default integration's override. It blocks the change if inherited extension handlers violate the canvas's hook checks. Neither action displays nor rewrites generated settings. Spec Kit 1.4.1 has no hook-only refresh command. If you choose a Spec Kit operation that regenerates agent settings, review its other effects first and reload the agent afterward; clearing the canvas warning only verifies the project files on disk.

If two owners conflict, disable the secondary extension or its competing hooks, then record the owner, rationale, and confirmation. For non-canonical local integrations with no automatic hooks, you can instead record disjoint output directories when the manifests declare compatible paths. The canvas rechecks declarations against `.speckit-companion/workflow-policy.json`; the policy does not constrain agent filesystem access or override the runtime.

An eligible GitHub integration offers **Review GitHub change** to close or reopen an existing issue, or set the single-select Status of one of its existing project items. On a workflow step that declares a literal `add-label` operation for an issue, **Review issue label** can apply that existing repository label as a separate manual change. It does not run the workflow, evaluate its conditions, or advance a checkpoint. The preview names the GitHub CLI account, target, field, and before/after values. The canvas rechecks them before making one write on confirmation; it never enables automatic project writes. Use the GitHub CLI on the canvas host with access to the selected issue or project.

On the constitution stage, **Draft constitution proposal** asks the agent for proposed text, not a file write. If the project owns its constitution directly, **Edit constitution** previews the exact Markdown before saving it. The canvas does not edit a constitution generated by Charter or a constitution-sync preset. Under **Constitution and Charter**, select a package-owned `<package>/.charter/constitution.md` that an enabled Charter installation has selected for distributed composition. **Review Charter source edit** previews and saves only that Markdown source, without fetching a registry or regenerating the project constitution.

On the Roadmap participant, **Review roadmap status change** updates one existing entry in Roadmap 0.1.1’s standard ledger. The preview shows the exact status, patch version, amendment date, and Sync Impact Report changes. This does not update feature state or GitHub. Custom configurations and unrecognized ledger formats are read-only.

On the Wireframe participant, **Review initial wireframe sign-off** uses Wireframe 0.1.1’s default layout and requires a passing review report with zero issues for each SVG. Visually review the raster previews before approving, or review the source files if they cannot be displayed. The reports do not prove which SVG revision was reviewed. Confirmation binds to the current SVGs, reports, and spec. It only adds the `UI Mockup` section; it does not regenerate drawings, change reports, or replace an existing sign-off.

On the adrkit participant, **Review ADR acceptance** requires a compatible adrkit 0.1.5 extension, adrkit CLI 0.20.0 on the host’s PATH, and a standard `docs/adr` corpus. Choose the decision and enter the human ratifier. adrkit checks the copied corpus, including quorum and objections. Confirmation saves only the exact proposed record shown in the preview; it does not commit or merge the decision.

On the PDaC Product participant, **Review approved Product Change** lists only hosted changes marked `status: approved`. The adapter requires enabled PDaC and PDaC Product 0.1.0, ProductShape CLI 0.26.1 on the host’s PATH, and the standard `v1alpha1` product layout. ProductShape performs a dry run and reports affected citations. The canvas previews up to eight model file changes and the hosted status update, repeats that preflight on confirmation, and writes only the displayed content. **Review Product Change archival** becomes available for changes marked `status: applied` and requires a separate confirmation. It previews the directory move and file digests, and leaves the product model untouched. Neither action commits or merges; a human merge still accepts the resulting baseline.

## Inspect workflow runs and decisions

Open **Workflow & runs** to pick an installed workflow and see its current definition, recent native Spec Kit run records, and any Companion review or guided checkpoint. The step diagram distinguishes conditional branches from fan-out, shows declared concurrency and join inputs, and links to installed subworkflows. It shows declared agents and inputs, not evidence that a specific agent ran. Recorded results list individual step occurrences separately so updated definitions don't rewrite history. When a native checkpoint records a fan-out expansion, its item outcomes appear under that expansion with the recorded item count and concurrency limit. This limit does not establish that the items ran at the same time.

The **Decision inbox** brings paused checkpoints together. Paused native runs take priority over other records in the 20-run view for each workflow; the inbox tells you if it found more paused checkpoints than it can display. A supported Companion gate opens the same reviewed verdict form as the configuration inspector, with its run, step, and evidence bound to confirmation. GitHub changes still require a separate confirmation. Native pauses are read-only in the canvas. Use **Copy resume command** from the run record and run it in an interactive terminal at the repository root; the canvas does not submit a verdict or run the command. Configuration blockers are listed separately from recorded outcomes. A native gate can link to the feature document or visual artifact its run record references, even if the workflow definition has since changed. Both recorded and definition references open the current repository copy, not a historical snapshot.

For an isolated or guided run, **Recorded gate decisions** lists the confirmed verdicts in order, with their timestamps and the source path and SHA-256 of any reviewed file. **Compare current evidence** opens the current file and tells you whether its bytes match the version reviewed. Companion stores the digest, not a copy of the file, so it cannot recover earlier contents. Earlier runs without these receipts are not backfilled.

To distinguish review from automated validation in the current definition, set `runAnnotations` in the version 1 Companion workflow policy. For example, `"runAnnotations": { "workflow:release:approve": "acceptance", "workflow:release:check": "validation" }` labels an existing human gate and an existing non-gate step. Keep the existing `decisions` array. Labels do not run checks, change step behavior, or grant approval.

## What the board shows

**Specs & runs** keeps the Spec, Plan, Tasks, and Activity tabs. Core documents show configured extension hooks, and Figma sections embedded in those documents are marked without claiming that the extension's verifier passed. Plan links to related design evidence; Tasks links to Agent Assign records and shows which HVE Core imports match the APM lockfile, even before a task is assigned. With Agent Assign 1.1.0, you can preview, add, or update an assignment to a verified project Claude Code profile. Confirming the first assignment creates `agent-assignments.yml`; no agent is run. Import agents through APM and validate or execute assignments in Claude Code; a Copilot-only profile is inspect-only.

On Tasks, **Preview HVE Core import** stages the pinned functional code reviewer using APM 0.36.1. It works in a project with no APM setup or an initialized Copilot-only `apm.yml` with an empty package list, no services or custom settings, and no lockfile. The host needs that APM version on `PATH` and access to public GitHub. Companion shows the manifest, lock receipt, and profile before confirmation; it adds one entry to an existing manifest without rewriting its comments or metadata. It writes only the three reviewed files and never runs the agent. Use APM directly for projects with installed packages or for other imports.

Separate tabs appear for artifacts that exist, such as architecture diagrams, data models, wireframes, prototypes, and decisions. Put exports under the feature folder (for example `diagrams/`, `wireframes/`, or `preview/`), or link a repository-wide decision under `docs/adr/` explicitly from a core document. PNG and SVG exports render as images. HTML has a structural preview with headings, tables, and disclosures, plus the original source. It does not execute prototype scripts, apply repository styles, or activate links and forms. Data Model Diagram exports show entities, fields, and relationship cardinalities. Simple `sequenceDiagram` exports show sender, recipient, and message order. Both keep the original Mermaid source; unsupported syntax, including sequence branches and loops, is shown as source only. Finding a file by convention does not identify which extension wrote it.

Illustrate's editable HTML under Architecture (or declared by its extension manifest) can also show a static diagram from its inline SVG, with the original HTML available below. The preview keeps supported shapes, text, and local arrows, not repository CSS, external resources, or animation. Use Illustrate's PNG or SVG export if you need the exact appearance.

For Preview 1.3.0, open **Preview** in the workflow inspector and choose a feature and fidelity. The dispatch preview shows the expected `preview/wireflow.html` output and requires both `spec.md` and `uc.md`. Confirmation sends the request to the agent; it does not mark the prototype as generated or approved. In the exported wireflow, Companion can replay declared button feedback as plain text in a unique status target or simple element ID. It turns links to an unambiguous heading or screen fragment within the same export into buttons that move keyboard focus. It does not run the producer's JavaScript, open external links, or submit forms.

An installed extension can declare additional read-only destinations in its manifest under `x-companion.specViews`. Each entry has a `phase` tab label and `path` to an existing supported file relative to the feature folder. Optionally add `documents` to link that evidence from Spec, Plan, or Tasks. For example, `{ phase: "Quality review", path: "quality/report.md", documents: ["plan", "tasks"] }` creates a **Quality review** tab and links to the report from both documents. Companion ignores paths outside the feature and does not run a command to generate missing files.

| Part | What you see |
| --- | --- |
| Spec list | Each spec's status, a four-step bar (specify, plan, tasks, implement) and its task count, most recently active first. Filter by Active, Done or All, or search by name or number. |
| Pipeline | The four steps of the open spec, each marked Not started, Running or Done |
| Next-step card | The step that comes next and the button that runs it, with the command it sends on the line below |
| Document tabs | The spec, plan, tasks, research, data model and checklists, rendered as they are in the VS Code viewer |
| Overview tab | The same record as [the Overview in VS Code](/docs/results/the-overview) |
| Activity tab | The run history, newest first |

## Choose the repository

By default the board follows its own session. It starts in the session's working directory and moves when the runtime reports that directory changed, for example when the session enters a new worktree. Each chat and each sub-session runs its own board, so parallel sessions in different worktrees never affect each other.

A Project chat usually sits in a conversation directory with no specs. The app gives a canvas no coordination context, so the board asks the runtime's session management for the sessions whose parent is this chat (`management.list`, filtered to `parentSessionId` equal to this session) and never scans other sessions. When this chat's own directory has no specs and exactly one such session exists, the board shows that session's worktree and follows it as it changes, appears or is archived. With several, the board lists them and waits: pick one in the list (or ask the agent for `select_child`), and the choice is saved like a manual one. Session management is the user's opt-in setting, which the board never turns on, and even when it is on the runtime may not report the app's Project sessions as children of the chat. The reliable route is a coordinator binding: the coordinating agent reads the child with its own `get_session` tool and calls the board's `bind_coordinated_session` action with the session id, the worktree path and a name. The board cannot verify that binding, and it does not follow later changes by itself, so the agent calls it again when the child is created, resumed, switched or moves to a new worktree. The binding is saved and outranks following. Refresh, opening a spec, running a step, **Use repository** on the directory already shown and reopening the panel all keep it. Only choosing a different directory or session replaces it, and **Disconnect from <name>** (shown instead of **Follow session** while bound) clears it and returns to the chat's own directory. Without any of these the board lists nothing and says why; open the board inside the child session to follow it automatically.

For a Project, ask the coordinator to populate **Coordinated session**. It calls `update_coordinated_sessions` with a complete snapshot of its own nonarchived sessions, including idle sessions, using scoped `get_sessions_status` and `get_session` for their actual worktrees. Choose one from the dropdown; no session is picked automatically. The list and selection survive reopening. The coordinator must refresh the snapshot after sessions are created, resumed, switched or archived, or their worktrees change; the board cannot verify ownership or detect these app changes itself. An updated path for the selected session rebinds the board, unless a step is in flight, in which case the update is rejected for retry. If the selected session disappears, the board marks it unavailable and retains its last repository until you choose another or disconnect. Commands still run in the chat that owns the board, not the selected session.

The move waits until no step sent from the board is running or being recorded, so a run is never read from another repository. A reopened panel catches up with the current directory.

An explicit choice overrides all of that. Press **Browse…** beside **Repository directory** to choose a folder, or enter an absolute checkout path and press **Use repository**. The native picker starts at the main worktree when the current directory belongs to a Git repository, otherwise at the current board directory. It runs on the extension host: it needs a local graphical desktop (and `zenity` on Linux), so on a remote or headless host enter the path manually. The board saves the choice in the session's artifact storage, restores it after reloads and in new panels, and stops following. Press **Follow session** (or ask the agent for `use_session_directory`) to drop the saved choice. A saved directory that no longer exists is ignored and the board follows the session instead. A chosen directory must be a repository root, with a `.git` or `.specify` folder in it; anything else is refused with a message. A missing spec directory shows a warning with the scanned path.
Ask the agent to select a repository to use the board's `select_root` action. For an initial selection, the agent can open the canvas with `{ "root": "/absolute/path/to/repository" }`; a saved selection takes precedence so an older open input cannot undo a later choice after a reload.

Changing repositories clears the selected spec and is blocked while a step sent from the board is running. Commands sent from a board outside the chat's working directory run in the chat that owns the board, and name the selected repository so relative paths resolve there; they are not routed into the child session.

## What each button sends

A button sends one command into the chat, and your agent runs the step from there. The board never edits a spec document itself.

| Button | Where | What it sends |
| --- | --- | --- |
| **New spec** | The header | Specify with your description, in the workflow you choose: Companion, Spec Kit, or Auto, which runs every step without pausing |
| **Run plan**, **Run tasks**, **Run implement** | The next-step card | The next step for the open spec |
| **Mark complete** | The card, once every step is done | [Mark complete](/docs/steps#mark-complete) |
| **Resume** | The card while a step is running, or the row under it | Picks a stopped run back up |
| **Doctor** | The row under the card | A health check of the run |
| **Ask Copilot** | The row under the card | A read-only question about where the spec stands |

With the Companion Spec Kit extension in the project, the buttons send `/speckit.companion.*`. Without it they send the stock Spec Kit commands, and Mark complete, Resume, Doctor, and the Companion and Auto choices on New spec aren't offered. A spec keeps the workflow it was started with, so one that was started on Spec Kit gets the stock commands even where Companion is installed.

The board spells each command the way your project registers it: `/speckit-plan` when the commands are skills, `/speckit.plan` when they're prompt files.

After a send, a note at the foot of the board names the command. **Show prompt** opens the whole message and **Copy** copies it, which is what you need when a session has no chat to send to.

## Step times without Companion

Companion records every step, so the Overview has a time for each one. In a stock Spec Kit project the board reads progress from the files instead: a written spec, `plan.md` or `tasks.md` marks its step done, and ticked tasks show how far Implement is. There the Overview times only the steps you sent from the board, because a step you typed into the chat yourself has no start the board could note.

## Known limits

- **The board is clipped after you narrow the panel.** Dragging the divider between the chat and the board leaves the board at its old width, cut off on the left, because the Copilot app doesn't resize the panel's page. Close the board and open it again after resizing.
- **Each session runs in a fresh worktree.** The app cuts it from your committed default branch, so it has no `node_modules`, and an implement step that runs tests installs the project's dependencies first. For the same reason, Companion's commands only resolve when they're committed as real files.
- **Opening the board starts nothing.** If your agent goes looking for work after opening it, ask "Only open it, then wait for me."
